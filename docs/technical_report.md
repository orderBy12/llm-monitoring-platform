# Technical Report: LLM Monitoring Platform

## Executive Summary

This report presents a practical monitoring and evaluation framework for a retrieval-augmented generation (RAG) system built around Azure OpenAI, LangChain, FAISS, SQLite, and Streamlit. The platform is designed to move beyond simple question-answering by instrumenting the full request lifecycle: document ingestion, retrieval, generation, logging, evaluation, drift detection, and dashboard-based monitoring. The repository implements a complete workflow that allows a team to observe system behavior, identify regressions, and assess the quality of model responses in a repeatable way.

The system is especially useful for teams deploying LLM applications in production, where response quality, latency, token usage, and semantic drift can change over time. Rather than treating the model as a black box, the platform turns the pipeline into an observable service with structured logs, quantitative metrics, and a visual dashboard.

## 1. Introduction

Large language model applications are increasingly being embedded in customer support, knowledge search, internal copilots, and enterprise assistants. While these systems are powerful, they often introduce reliability challenges such as hallucinations, latency spikes, prompt regressions, and semantic drift. A production-grade LLM stack therefore requires monitoring mechanisms that go beyond basic logging.

The repository presented here addresses this need by providing an end-to-end monitoring platform for a RAG-based assistant. It combines retrieval over curated knowledge documents with Azure-hosted language and embedding models, while simultaneously capturing operational and quality metrics. The result is a system that supports both engineering monitoring and model quality evaluation.

The project is organized around a set of sequential tasks, each responsible for a distinct layer of the monitoring pipeline:

- document setup and vector index construction
- RAG query execution
- request logging and storage
- token and latency tracking
- RAG quality evaluation
- embedding drift detection
- edge-case testing
- dashboard visualization

## 2. System Architecture

The architecture follows a modular pipeline that separates retrieval, generation, logging, evaluation, and presentation. At a high level, the platform performs the following flow:

1. Source documents are loaded from the data directory and transformed into vector embeddings.
2. The embeddings are stored in a FAISS index for efficient similarity search.
3. A user query is converted into an embedding, relevant chunks are retrieved, and the answer is generated by Azure OpenAI.
4. The request is logged to both CSV and SQLite for durable storage.
5. Evaluation workflows score the response using an LLM-as-judge approach and compare the output against the retrieved context.
6. Drift detection measures whether embedding behavior changes over time by re-embedding a fixed set of reference queries.
7. Results are surfaced through a Streamlit dashboard for operational monitoring.

This architecture is intentionally modular. Each stage can be executed independently, which makes it easier to debug, test, and extend. In addition, the use of SQLite as the central operational store allows the dashboard and analysis scripts to reuse the same data source.

## 3. Core Components and Implementation Details

### 3.1 Vector Index Construction

The setup stage loads domain-relevant documents from the data folder and preprocesses them into chunks. These chunks are then embedded using Azure OpenAI embeddings and indexed with FAISS. This step creates a local retrieval index that enables fast semantic search over the knowledge corpus.

This component is essential because the performance of the overall system depends strongly on the quality of retrieval. If the retrieval step fails to surface relevant context, even a strong language model will produce weaker answers.

### 3.2 RAG Query Pipeline

The core query pipeline follows a standard RAG pattern:

- embed the user's question
- retrieve the most relevant chunks from the vector store
- augment the prompt with the retrieved context
- generate a response with Azure Chat OpenAI

This design is lightweight and transparent. It supports experimentation with different prompt versions and allows the system to log metadata for each request, including prompt version, retrieval latency, completion latency, and token counts.

### 3.3 Logging Middleware

A dedicated logging layer captures each request and stores the information in two forms:

- CSV for simple inspection and portability
- SQLite for structured querying and dashboard use

The logger records request identifiers, timestamps, user queries, retrieved context, sources, model name, prompt version, model response, token counts, latency values, and safety/error metadata. This layer is a critical part of the platform because it transforms transient request execution into durable, analyzable telemetry.

### 3.4 Evaluation Layer

The evaluation module uses an LLM-as-judge methodology to score every response on three quality dimensions:

- context relevance
- faithfulness
- groundedness

These metrics approximate the quality of the RAG response without requiring a rigid gold-standard dataset. The evaluator sends the question, retrieved context, and answer to an Azure OpenAI judge model, which returns structured scores and reasoning. This makes the platform suitable for monitoring relative quality over time, even when human-labeled evaluations are not available.

### 3.5 Drift Detection

Embedding drift is measured by re-embedding a fixed set of reference queries and comparing their current vectors against a stored baseline. The system calculates cosine similarity and converts it into a drift score. A low score indicates stable embedding behavior, while a high score suggests that the embedding space has changed significantly.

This is important because retrieval quality can degrade gradually even when the application itself continues to run. Drift monitoring offers an early warning signal for semantic shifts in the underlying embedding model or document corpus.

### 3.6 Edge-Case Stress Testing

The repository also includes adversarial and boundary-condition prompts. These are designed to test whether the system behaves safely and consistently under unusual conditions, such as prompt injection attempts, ambiguous wording, and mixed-language queries. By explicitly testing failure modes, the platform supports robustness analysis rather than relying solely on average-case performance.

### 3.7 Dashboard

The Streamlit dashboard provides a live view of the monitoring system. It presents KPI cards, charts, and tabular views for:

- token and cost usage
- latency trends
- RAG evaluation scores
- drift status
- raw logs

This user-facing layer makes the monitoring system accessible to both technical and non-technical audiences.

## 4. Monitoring Methodology

The monitoring framework is built around a combination of operational telemetry and quality assessment. The system captures both system-level metrics and response-level quality signals.

### 4.1 Operational Metrics

Operational measurements include:

- request volume
- token usage
- estimated cost
- retrieval latency
- LLM latency
- end-to-end latency
- error rate
- safety flags

These indicators help teams understand whether the application is performant and financially sustainable.

### 4.2 Quality Metrics

Quality metrics focus on whether the answers are useful, grounded, and faithful to the retrieved context. The evaluation score is a composite of the three judge-based metrics. In addition, the workflow highlights hallucination signals and low-quality answers, which are especially important in enterprise settings where factual correctness is essential.

### 4.3 Monitoring Workflow

The repository supports the following practical workflow:

1. build the FAISS index
2. run the RAG pipeline and generate logs
3. analyze token and latency performance
4. evaluate response quality
5. detect embedding drift
6. run edge cases and review failures
7. view results in the dashboard

This sequence makes the platform suitable for both periodic reporting and continuous monitoring.

## 6. Limitations and Considerations

Despite its strengths, the platform has several practical limitations:

- It depends on external Azure services for embeddings and chat completions, making it sensitive to API configuration and availability.
- The LLM-as-judge setup is powerful but can itself be inconsistent or biased, especially on adversarial or ambiguous prompts.
- The system relies on local storage for the vector index and monitoring database, which is appropriate for development but may need scaling for larger deployments.
- The evaluation process uses tokens and model calls, which introduces cost and latency overhead.

These limitations are not blockers, but they should inform how the system is deployed and used in production. For example, a mature deployment might include rate-limiting, caching, threshold-based alerts, and a larger evaluation dataset.

## 7. Conclusion

The LLM Monitoring Platform demonstrates a practical and extensible approach to observing and evaluating a RAG system. It brings together retrieval, generation, logging, quality scoring, drift detection, edge-case stress tests, and visualization into a single workflow. Its value is not only technical but also organizational: it helps teams understand whether their AI system is healthy, stable, and improving over time.

The repository provides a strong foundation for further development. Future enhancements could include automated alerting, A/B testing of prompts, human-in-the-loop evaluation, more advanced drift baselining, and a production-grade deployment architecture. In its current form, however, the platform already offers a credible blueprint for responsible LLM monitoring and evaluation.
